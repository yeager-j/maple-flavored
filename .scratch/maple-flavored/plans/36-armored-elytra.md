# Plan: ticket 36, Armored Elytra (Maple Flavored, Fabric 26.3)

Ticket: `.scratch/maple-flavored/issues/36-armored-elytra.md`. Spec: `.scratch/maple-flavored/spec.md` lines 206-208, 411, 417, 421, 536. Design: `.scratch/maple-flavored-design/issues/06-material-roles-and-alloys.md` "Armored Elytra"; advancement table in `17-advancements.md` (End, "Get an Armored Elytra", parent Sky's the Limit, goal, no reward).

## End goal

A player who has invested in a full Alloy set can fly without giving up its chest piece: armor, Alloy traits, damage reductions and set bonus all stay. The cost is flight, so a plain Elytra stays the travel choice. Done = five items (one per Alloy) obtainable at a Smithing Table, behaving as that Alloy's chestplate for every non-flight rule, gliding with the two penalties, stopped by Grounded, with an advancement and GameTests.

## Decisions

1. **Items live in `AlloyGear`, as the Alloy's chest piece.** `AlloyGear` registers, per Alloy, `{alloy}_armored_elytra` and maps it in `PIECES` to `Piece(alloy, GearKind.CHESTPLATE)`. So `alloyOf` / `kindOf` / `piecesWorn` / `AlloySets.fullSet` / `AlloyDamage` / Orichalcum Illager neutrality / the trait components (`addTraits`: durability %, slot modifiers) all apply with zero new branches. `kindOf` is only consulted for held tools (PICKAXE / isHeld), so CHESTPLATE is truthful: "it counts as the chest piece". `GearKind` is NOT extended (it means "has a Netherite version"; recipes, tags, models, tabs iterate it).
   - Properties: `GearKind.CHESTPLATE.properties(...)` (vanilla `humanoidArmor`, so same durability, attributes, enchantability as the chestplate), then `.component(GLIDER)`, `.component(EQUIPPABLE, Equippable.builder(CHEST).setEquipSound(netherite equip sound).setAsset(maple_flavored:{alloy}_armored_elytra).build())` (damageOnHurt stays true, like armor), `.rarity(EPIC)` like the Elytra, `.fireResistant()`, `.repairable(alloy.ingot())`.
2. **Recipe: base = the Alloy chestplate, addition = Elytra, no template.** The base's components carry (trim, name, wear, and later Reinforcement from ticket 37); the Elytra is consumed. Plus Armored Elytra of another Alloy + this Alloy's ingot changes Alloy, like all Alloy gear (spec 411). Netherite chestplate + Elytra matches nothing. Generated by `AlloyGearRecipes` datagen.
3. **Enchanted inputs are refused.** Existing rule refuses an enchanted base. Extend `MaterialUpgrades.refuses` to take the whole `SmithingRecipeInput` and refuse when base or addition is enchanted, so an enchanted Elytra's Mending isn't silently deleted. Alloy ingots are never enchanted, so other recipes are unchanged. The existing tooltip "Can't upgrade enchanted items" covers it.
4. **Enchanting = a chestplate's.** Add the five items to `#minecraft:enchantable/chest_armor`, `enchantable/durability`, `enchantable/equippable` (the enchantable tags that hold `#chest_armor`), NOT to `#chest_armor` itself, which would make it trimmable. Electrum's goes in `maple_flavored:extra_enchantment_slot` and `#minecraft:piglin_safe_armor`. New tag `maple_flavored:armored_elytras`. Material unit: its REPAIRABLE is the Alloy ingot, so `MaterialUnits` gives 1 unit, no code change.
5. **Flight, in a new `alloys/ArmoredElytraFlight` (common source set, runs both sides):**
   - `Vec3 afterGlideDrag(LivingEntity, Vec3 movement)`: if the chest item is an Armored Elytra, `movement.multiply(0.995, 1, 0.995)`. Hooked by `@ModifyReturnValue` on `LivingEntity.updateFallFlyingMovement` in the existing `LivingEntityMixin`.
   - `Vec3 boostedMovement(LivingEntity, Vec3 current, Vec3 boosted)`: if armored, `current + (boosted - current) * 0.75`. Hooked by a new `FireworkRocketEntityMixin` `@WrapOperation` on the `LivingEntity.setDeltaMovement(Vec3)` call in `tick` (only the attached-glider branch calls it on a LivingEntity).
   - Constants, not game rules: they run on the client too and game rules don't sync.
   - Grounded needs nothing new: `LivingEntityMixin.canGlide` already covers any glider.
6. **Rendering.** Equipment asset `{alloy}_armored_elytra.json`: `humanoid` + `humanoid_baby` layers = the Alloy's chestplate texture (`maple_flavored:{alloy}`), `wings` layer = `maple_flavored:{alloy}` with `use_player_texture: true` (capes still show, like vanilla). New textures, recoloured from Mojang's Elytra by the same palette as the Alloy chestplates (Netherite body greys + Alloy trim): `textures/item/{alloy}_armored_elytra{,_broken}.png`, `textures/entity/equipment/wings/{alloy}.png`. Item model via datagen `generateElytra` (broken variant). CREDITS.md entry. Vanilla draws a trim on every equipment layer but baby armor, and no vanilla wings are trimmable, so a trimmed chestplate's trim would put missing textures on the wings: the client `EquipmentLayerRendererMixin` drops the trim for the `wings` layer only, keeping the stored trim and its body render (plan review finding).
7. **Creative tab:** after the Elytra, wherever it is shown.
8. **Advancement** `maple_flavored:end/obtain_armored_elytra`, parent `minecraft:end/elytra`, frame goal, `inventory_changed` on `#maple_flavored:armored_elytras` (vanilla trigger is enough; no custom trigger). Title "Flying Fortress", description "Combine an Elytra with an Alloy chestplate at a Smithing Table".
9. **Lang:** "Steel Armored Elytra" etc.

## Public API sketch

```java
// AlloyGear
public static Item armoredElytra(Alloy alloy);
public static boolean isArmoredElytra(ItemInstance item);
// alloyOf / kindOf / piecesWorn unchanged; they now also recognise Armored Elytra (kind CHESTPLATE).

// MaterialUpgrades
public static boolean refuses(SmithingRecipeInput input); // was refuses(ItemStack base)

// ArmoredElytraFlight (new)
public static Vec3 afterGlideDrag(LivingEntity glider, Vec3 movement);
public static Vec3 boostedMovement(LivingEntity glider, Vec3 current, Vec3 boosted);
```
Consumers: `LivingEntityMixin`, new `FireworkRocketEntityMixin`, `SmithingTransformRecipeMixin` + `SmithingMenuMixin` (refusal), datagen (`AlloyGearRecipes`, `AlloyGearModels`, `AlloyGearTags`), gametests.

## Tests (new `ArmoredElytraGameTests`)

1. Each Alloy chestplate + Elytra smiths into its Armored Elytra (menu: both inputs consumed); Netherite chestplate + Elytra, and Elytra base + chestplate addition, make nothing.
2. Trim, name and wear share carry from the chestplate.
3. Armored Elytra + different Alloy ingot changes Alloy; same ingot makes nothing.
4. Enchanted chestplate or enchanted Elytra is refused, and the menu reports the refusal.
5. Protects like the chestplate: every component equals the chestplate's except name, model, equippable, glider, rarity; equippable slot CHEST with damage on hurt; `canGlideUsing` true; a player wearing it has the chestplate's armor/toughness.
6. Enchanting: for every registered enchantment `canEnchant` matches the chestplate's; Electrum's has the extra slot tag; material is the Alloy ingot, 1 full-repair unit.
7. Set bonus: helmet, Armored Elytra, leggings, boots of one Alloy is a full set (Steel modifiers applied); a different Alloy's Armored Elytra breaks it; `piecesWorn` counts it.
8. Flight: two mock players gliding with the same velocity and look; one `travel` step: armored horizontal velocity = plain × 0.995, vertical equal. One rocket `tick` each: armored change = 0.75 × plain change.
9. Grounded: a Grounded player with an Armored Elytra can't start gliding; a free one can.
10. Advancement granted on getting one.

11. Client screenshot test `ArmoredElytraClientGameTest`: plain, trimmed and enchanted Armored Elytra on stands, front and back, and on the player, checked by eye (with a negative control: without the wings guard the trimmed one's wings are magenta).

Both test classes are registered in `src/gametest/resources/fabric.mod.json`.

Checks: `gradlew runDatagen`, `gradlew runClientGameTest`, `gradlew build`, `gradlew runGameTest` (full suite). Hand check left in the ticket: flight feel, Grounded, worn look.
